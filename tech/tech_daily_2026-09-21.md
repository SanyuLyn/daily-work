## Flutter

### [2026 Flutter VS React Native，同时在 AI 时代 VS Native 开发，你没见过的版本](https://zhuanlan.zhihu.com/p/2012656976363020316)
**摘要**：把跨端框架之争放到 AI 时代重新算了一遍账。渲染侧给出的基准数据是：相比旧的 Skia 渲染器，Impeller 在复杂动画场景下卡顿帧减少 30%~50%，Flutter 实测掉帧率接近 0%，而 React Native 为 15.51%，自绘引擎在动画密集场景的确定性优势依然明显。但文章认为 2026 年真正变化的不是性能曲线，而是生态位：原生、跨端、AI 生成式 UI 三者的分工被重新划分，框架选型不再只看「一套代码多端跑」，而要看谁更容易接入 Agent 工具链、谁的 UI 描述更适合被大模型生成和修改。结论偏向「按场景混用」，而非一刀切站队。

### [Flutter 2026 Roadmap 发布，未来计划是什么？](https://zhuanlan.zhihu.com/p/2009657387510952563)

## Android

### [Android 17 正式发布！target 37 一大批旧代码直接不能用了](https://zhuanlan.zhihu.com/p/2052311127107883359)
**摘要**：以「破坏性变更清单」的视角梳理 targetSdk 升到 37 之后失效的旧写法。文章的判断是，这一版不是单纯加 API，而是系统级控制模型的一次重构：权限、内存、后台行为、硬件访问几条线同时收紧，很多长期沿用的兼容写法在 target 37 下会直接抛异常或被系统静默拦截。作者建议团队不要把升级当成发版前的体力活，而应提前建立一份内部「不可用 API 清单」并接入 CI 静态检查，同时用灰度包在真机上跑一轮核心链路。考虑到 Google Play 的强制截止在 2027 年 8 月，窗口期看似宽裕，但涉及底层库和三方 SDK 的改造往往才是长尾。

### [Android 17 内存管理将严格管控，App 要注意适配](https://zhuanlan.zhihu.com/p/2045807688592913359)
**摘要**：专讲内存这一条线。Android 17 会按设备总 RAM 给应用划定更严格的内存上限，超限进程可被系统直接终止，而不再只是提高被回收的优先级。这对图片密集型、地图型、音视频类以及大量使用 Native 堆的应用冲击最大，因为这类应用的峰值内存往往来自 Native 侧，传统只盯 Java 堆的监控会失真。文章给出的适配方向包括：建立分机型（按 RAM 档位）的内存预算，Native 与 Java 双侧打点，用 Baseline/大图降采样与及时释放控制峰值，以及在低配机型上主动降级功能。核心提醒是「别等线上 OOM 率暴涨再查」。

### [Android 17 来了！新特性介绍与适配建议](https://zhuanlan.zhihu.com/p/2012175791899844808)
**摘要**：偏综述性的适配入门，把 Android 17 的变化归到几条主线并给出优先级。除权限与内存外，重点提到大屏与自适应：Android 17 强化全屏适配要求，推荐直接使用 Compose Adaptive 相关库来处理自适应导航、多面板布局与动态窗口状态，而不是继续用方向枚举加手写分支。文章同时提到 Google 在开发者工具侧的动作——推出 Jetpack Compose adaptive 相关的 AI 工作流，用来辅助生成自适应布局、FlexBox/Grid 与非触控输入的处理代码。建议的落地顺序是：先过一遍破坏性变更，再做大屏自适应，最后才是接入新的 AI/智能体接口。

### [截至 2026 年，安卓各版本份额？](https://zhuanlan.zhihu.com/p/2024215004325356791)
**摘要**：用版本分布数据回答「最低支持到哪一版」这个老问题。文章给出的口径是：到 2026 年 3 月，Android 15 已成为国内的主流版本，Android 16 仍主要集中在旗舰机型与小规模分发，尚未形成规模。这组数据的实际用途是反推 minSdk 与兼容策略——主流盘子在 15 附近意味着新 API 的直接可用率仍然有限，大量新特性仍需做降级路径；而 targetSdk 必须跟着最新版走，二者不能混为一谈。对需要覆盖下沉市场和海外新兴市场的应用，文章建议把版本分布按地区分开统计，全球平均值往往掩盖了区域差异。

### [新 · Jetpack Compose：从上手到进阶再到高手](https://zhuanlan.zhihu.com/p/1962840061306447121)
**摘要**：配合 Google 官方「Compose First」表态的系统性学习材料。官方已明确新的 Android API、库、工具与开发者指南都将围绕 Jetpack Compose 优先设计，而传统 View 体系以及 Fragment、RecyclerView、ViewPager 等基于 View 的 Jetpack 库进入维护模式，这意味着存量项目继续留在 View 体系上会越来越难享受新能力。文章从上手、进阶到原理逐层展开，涵盖组合（Composition）、重组（Recomposition）与测量-布局-绘制三阶段的关系，并落到性能优化——通过 Baseline Profile 让 ART 在安装期提前编译关键路径代码，以缓解 Compose 作为独立库带来的冷启动开销。
